# 闪传 FlashDrop · 局域网互传

微信"文件传输助手"式的局域网互传工具：**电脑 ↔ 电脑、电脑 ↔ 手机、手机 ↔ 手机**，互发文字、图片和任意文件。全程局域网直连，**不经过任何互联网服务器**，数据不出内网。

**当前版本 v1.13.1**（作者 Thomajesty · Thomajesty@163.com，双端设置内可查看）。

> **升级安装**：v1.1.0 及之后版本使用固定签名密钥，**可直接覆盖安装**，无需卸载（仅从 v1.0.x 及更早升级时需先卸载一次）。电脑端 EXE 直接替换运行即可。

## 交付物

| 文件 | 说明 |
|---|---|
| `FlashDrop.exe` | Windows 端（Win10/11 64位，绿色单文件，无需安装） |
| `FlashDrop.apk` | Android 端（Android 7.0 / API 24 起） |
| `PROTOCOL.md` | 通信协议规范（供二次开发/互通参考） |

## 快速开始

1. 电脑双击 `FlashDrop.exe`，手机安装 `FlashDrop.apk` 并打开；
2. 确保所有设备连接**同一个路由器**（同一 Wi-Fi / 同一局域网）；
3. 首次启动后设备会**自动互相发现**（约 1~5 秒），左侧/顶部列表出现对方设备；
4. 选中目标设备（或"全部设备"），即可互发文字、文件、图片。

### Windows 首次启动提示

- 弹出"Windows 安全中心警报"时请点 **允许访问**（勾选"专用网络"和"公用网络"）；
- 若错过弹窗，可在 应用内 ⚙ 设置 → 网络 → "允许 Windows 防火墙入站" 重新触发。

## 功能一览

- **自动发现**：UDP 广播 + 组播，打开即用，无需输入 IP；
- **同机跨版本身份统一**：同一台设备先后运行不同版本（或重装），自动合并为一条设备（聊天记录一并迁移），不会显示成两台；
- **单实例运行**：重复启动不会开第二个窗口，自动唤起已运行的窗口（Windows）；
- **在线设备列表**：实时显示所有在线设备（电脑/手机图标区分），离线自动标记；
- **设备名默认为主机名**：旧版"某某的电脑"配置会自动迁移为主机名（可在设置中自定义）；- **多端同步发送**：电脑可勾选多台设备（或"全部设备"）一次群发，每台独立进度；
- **文字消息**：Enter 发送，Shift+Enter 换行，带"已送达"回执；
- **消息管理（微信式）**：
  - Windows：右键消息 → 复制 / 多选 / 删除（大字号菜单）；多选模式支持全选、批量删除；
  - Android：长按消息在气泡上方弹出二级菜单（复制 / 删除 / 多选）；多选模式点击消息勾选，支持全选、批量删除；
- **文件/图片**：单个最大支持数 GB（512KB 分块 + MD5 校验 + 断点清理）；
  - Windows：📎 发送文件 / 🖼 发送图片 / 📋 发送剪贴板 / 直接拖拽文件进窗口；
  - Android（微信文件助手式交互）：
    - 底部输入胶囊 = 相册快捷键 ＋ 输入框 ＋ 圆形"＋"；输入文字后"＋"自动变为圆形**发送键**（固定右下）；
    - 点"＋"从底部弹出功能面板（**相册 / 拍照 / 文件** 圆角卡片）；点输入框或聊天区自动收起；
    - 超过 3 行时输入框**右上角出现对角展开键**（随文字升高），全屏输入页支持：
      - 打开时整页**向上推起**动画；右上角关闭；右下角圆形发送键直接发送；
      - 全屏状态下**向下拉**即可收起，恢复 3 行输入状态；
    - 空输入框长按 = 粘贴 / 全屏输入；选中文字后出现原生的全选/剪切/复制/粘贴工具条；
    - 文字消息长按直接进入拖选模式（部分选中弹出复制/全选；全部选中时出现复制/多选/删除）。
- **接收控制**：默认自动接收；关闭"自动接收"后每个文件需手动点"接收/拒绝"；发送失败/中断的消息可**一键重发**（双端）；
- **异步待发送（v1.9.0，双端）**：在「全部设备」视图发送时，**只要当前没有任何在线设备，内容就先保存到待发送队列**并在聊天区显示"⏳ 待发送"气泡，**任意设备上线后自动补发**（文本和文件一视同仁，重启也不丢）。顶栏「⏳ 待发送 N」按钮可打开**待发送管理窗口**，逐条查看目标与时间、**立即发送 / 删除 / 清空全部**；
- **离线待发队列（双端）**：发文件时目标设备不在线？文件会**先保存下来**并在聊天区显示"⏳ 待发送"消息（可取消），**对方一上线自动发出**并正常显示送达（重启也不丢）；
- **链接识别（双端）**：聊天里的网址自动识别——电脑端气泡下方出现链接按钮**点击直接打开**，右键还可"打开/复制链接"；手机端点击链接弹出**复制 / 打开**；
- **传输加密（TLS，双端可选）**：设置 → 网络/开关里开启后，与同样开启的设备自动以 TLS 加密通信；对未开启的设备自动回退明文，无需重启、立即生效。剪贴板截图可直接 **Ctrl+V 粘贴发送**（电脑端），输入框右键菜单为中文；
- **息屏提醒（Android）**：离开应用或息屏时收到消息/文件会弹**系统通知**，点击回到聊天；
- **系统分享入口（Android）**：在微信/相册/文件管理器里点"分享 → 闪传"，直接发给最近在线的设备；
- **新消息提示（Windows）**：上翻阅读历史时不打断，新消息到达会在聊天区右下角浮现"⬇ 有新消息"，点击直达底部；
- **开机自启（Android，可选）**：设置内开启后，手机重启自动恢复接收服务；
- **传输进度**：实时进度条 + 速度，可随时取消（双方同步取消）；
- **聊天记录**：本机保存；单条右键/长按删除、多选批量删除，设置内可**一键清空全部记录**；
- **图片预览**：收到的图片直接在聊天中显示缩略图（Windows，双击打开原图）；Android 端图片消息**不套气泡直接显示**（微信式，保持宽高比），下方小字"文件名 · 大小"，点开为原图查看器（点任意处关闭，底部 保存到相册 / 转发 到微信、QQ、飞书等任意应用）；
- **主题**：深色 / 浅色 / **跟随系统**（系统切换深浅色时自动跟随，双端支持；Windows 标题栏与所有弹窗同步跟随）。

- **对话框配色**：设置 → 基本 → 对话框配色（闪传蓝/微信绿/清新紫/暖橙/樱花粉），保存后立即生效并在屏幕中间弹出 2 秒提示；发送侧气泡按方案着色、宽度随内容自适应；文件消息为透明信息卡片（名称+大小），图片显示缩略图（点击可打开查看，Android 端查看页支持保存到相册）。
- **全局气泡（v1.2.0）**：你设置的配色会随新发出的消息一起送达——**所有接收方的屏幕上，你发的气泡都显示你的配色**；更早的历史消息保持原样不受影响。

## 按设备分会话（v1.8.0，类微信多会话）

**每台设备 = 一个独立会话**，和微信"切换聊天对象"完全一致：

| 位置 | 行为 |
|---|---|
| **Android 顶栏设备选择栏** | 宽度前移占据主位；选中哪台设备，聊天区**只显示与该设备的内容**；发消息/发文件也只发给它。"全部设备"= 汇总视图 |
| **Android 接收文件** | 按设备分文件夹：`下载/FlashDrop/<设备名>/xxx`（如 `下载/FlashDrop/小米 14/报告.pdf`） |
| **Windows 接收文件** | 同样按设备分文件夹：`接收保存位置\<设备名>\xxx` |
| **跨端一致** | 手机和电脑对**同一台设备**生成**同名文件夹**（非法字符统一替换为 `_`，如 `小米: 14/Pro` → `小米_ 14_Pro`） |
| **Windows 侧栏** | 沿用原有设计：点左侧设备即切换会话 |

要点：
- 聊天记录本来就是**每设备一个独立文件**（`history/<设备ID>.jsonl`），本次把 Android 界面也接上；
- **群发消息**在每个目标设备的会话里都会显示（不会出现"切到某设备消息不见了"）；
- 没有明确目标的消息（分享入口直发）在所有会话里都可见；
- 设备名会做安全净化（`\ / : * ? " < > |` 与控制字符 → `_`），并**阻断目录穿越**（`..`）。

## 删除与清理（v1.10.0 重做）

> v1.10.0 把删除交互从"逐条消息勾选"改成"**按类型多选**"，并修掉了 v1.8.0 起就存在的
> **点删除必闪退**缺陷（根因见文末 v1.10.0 章节）。

### Android 顶栏「删除」（作用域 = 当前链接设备）

顶栏设备选择栏右侧、**「扫描」后面红色「删除」按钮**，点击弹出**按类型多选**窗口：

- 三个分类 CheckBox，各自带实际条数：

  | 分类 | 含义 |
  |---|---|
  | **下载文件** | 非图片文件（`svg` 也归此类，因为不是可预览图片） |
  | **接收图片（未保存到图库）** | 收到并存在 `下载/FlashDrop/` 下的图片（未手动存图库的） |
  | **聊天记录** | 文字消息 |

- **默认全部不勾选**；某类没有内容时该行**置灰不可勾选**；
- 勾选区下方有 **「全选」按钮**（点一次全选，再点变「取消全选」）；
- 最下面一排是 **「取消」** 和 **「删除」** 两个按钮；
- 点「删除」后再弹**二次确认**，逐项列出即将删除的类型，确认才真正执行；
- **删除范围 = 设备选择栏当前选中的那台设备**：
  - 聊天记录只清该设备的历史；
  - 文件/图片只删 `下载/FlashDrop/<该设备名>/` 下的对应类型；
  - 选「全部设备」时才会作用于所有设备。

### Android 设置内「数据清理」（作用域 = 全局）

设置页原先的 4 个按钮（清空聊天记录 / 删除下载文件 / 删除下载图片 / 打开保存目录）
**在 v1.10.0 合并为一个「数据清理」按钮**：

- 点击弹出**同样的三类多选窗口**（下载文件 / 接收图片（未保存到图库）/ 聊天记录），
  底部同样有**「全选」**，最下面 **「删除」/「取消」**；
- **清理范围是全局的：app 内所有连接设备**的聊天记录与已接收文件，不限于某一台；
- 弹窗会**实时统计每一类的实际条数**并显示在分类标题里，所见即所删；
- 若本机没有任何可清理内容，会直接提示"暂无聊天记录，也没有已接收的文件"；
- 下方保留一个低调的**「查看保存位置」**文字入口（v1.10.1 起，见下方说明）。

> Android 11+ 对非本应用创建的文件会弹系统确认框（这是系统限制）。
> 删除不可恢复；删完返回聊天界面会自动刷新。

### 聊天记录与文件「成对删除」（v1.10.1）

在**主界面**选中某台设备后点 🔍 后面的删除按钮，勾选「下载文件」或「接收图片」时，
**对应的聊天气泡记录会同步消失**，不是只删磁盘文件、界面上还留着一条空记录。
三类都是「记录 + 文件」成对处理：

| 勾选类型 | 删聊天记录 | 删磁盘文件 | 删历史文件条目 |
|---|:---:|:---:|:---:|
| 下载文件 | ✅ | ✅ | ✅ |
| 接收图片（未保存到图库） | ✅ | ✅ | ✅ |
| 聊天记录 | ✅ | — | ✅ |

> 同时清理了内存中的传输索引（`byMid` / `byTidIn` / `byTidOut`），
> 所以删掉的消息不会被后续到达的传输进度事件"复活"。

### 「查看保存位置」（v1.10.1 替换原「打开保存位置」）

**为什么不再直接跳文件管理器**：接收目录是公共的 `下载/FlashDrop`，
本应用无权把它暴露成一个可浏览的目录提供者（`FdFileProvider` 只能打开**单个文件**，
不支持目录浏览）；唯一能跳的 `content://com.android.externalstorage.documents/...`
又依赖目标文件管理器实现 DocumentsContract，**国产 ROM 的第三方文件管理器普遍不实现**——
结果就是"能拉起文件管理器、随即立刻弹回本应用"，比不提供这个按钮更让人困惑。
该问题无法修复，故按需改为下面这个 **100% 可用** 的方案。

**现在的用法**：

1. 设置页点「查看保存位置」→ 弹窗直接显示**完整真实路径**
   （如 `/storage/emulated/0/Download/FlashDrop`）；
2. 弹窗里**列出已有的各设备子目录及文件数**（如 `小米 14_ Pro_测试（12 个文件）`）；
3. 点「**复制路径**」→ 路径进剪贴板 → 打开**任意**文件管理器，
   在**地址栏粘贴**回车即可直达该目录。

> 还没有任何设备目录时，弹窗会提示"还没有设备文件夹，收到文件后会自动创建"。

## 多路由器 / 级联环境说明

本软件专门优化了**多路由器级联**场景（如：光猫→路由器A→路由器B，设备分别接在 A、B 下）：

- **第二级路由下的设备主动连第一级**（方向通常可达），连接后双向复用同一条链路，收发都不受影响；
- 软件每 30 秒自动扫描常见网段（192.168.x.x、10.x.x.x、172.16-31.x.x 等），跨网段设备自动被找到；
- 找不到时点 **⟳ 深度扫描**（覆盖更全，约 10~60 秒）；
- 极端情况（AP 隔离等）用 **＋ 添加** 手动输入 `对方IP`（默认端口 58899）直连。

## 命令行参数（Windows）

```
FlashDrop.exe [--port 58899] [--connect 192.168.1.101[:端口]] [--hidden]
  --port      指定服务端口
  --connect   启动后立即连接指定设备
  --hidden    启动后最小化到托盘
```

## 常见问题

| 现象 | 处理 |
|---|---|
| 看不到对方设备 | 1) 确认同一局域网；2) 允许防火墙；3) 点"深度扫描"；4) 手动添加 IP |
| Windows 无法收到文件 | 防火墙未放行入站（设置→网络→一键放行） |
| Android 收不到 | 系统设置里允许闪传"后台运行/无限制省电"；通知权限建议打开 |
| 同一台电脑开两个实例 | 用不同端口：第二个实例加参数 `--port 58900`（同端口会冲突） |
| 端口被占用 | 设置里改端口（1024~65535），重启应用 |

## 安全与隐私

- 所有通信仅在本局域网内完成，**无互联网服务器、无账号、无遥测**；
- 默认传输内容未加密（与局域网内 SMB/飞秋等同类工具一致）；如需加密，双端在设置中开启 **传输加密（TLS）**，与同样开启的设备通信时自动加密，未开启的设备自动回退明文；
- 加密采用设备内置自签名证书，适合家庭/办公等可信局域网；请勿在不可信的公共 Wi-Fi 中传输敏感内容。

## 技术参数

- 协议版本 v1（详见 `PROTOCOL.md`）：TCP 58899（帧：4 字节长度 + JSON/二进制块）+ UDP 广播/组播发现；
- 单块 512KB，MD5 全文件校验，自动重命名避免覆盖，.part 缓存防中断损坏；
- Windows：Python 3.12 + PySide6 打包（PyInstaller 单文件）；Android：纯框架 API（无第三方依赖），minSdk 24 / targetSdk 34。

## v1.7.6 变更（2026-10-4）——链接渲染闪退根因修复【已定位】

### 崩溃根因（来自真机日志 samsung SM-S9180 / Android 16 API 36）
```
java.util.regex.PatternSyntaxException: Syntax error in regexp pattern near index 10
[.,;:!?)]}$
          ^
    at com.flashdrop.app.FdUtil.firstUrl(FdUtil.java:273)
    at com.flashdrop.app.MainActivity.bind(MainActivity.java:1584)
    at com.flashdrop.app.MainActivity$MsgAdapter.getView(...)
```

**Bug**：`FdUtil.firstUrl()` 里的 `m.group(1).replaceAll("[.,;:!?)]}$", "")` —— 字符类 `[...]`
结束后紧跟 `$`（正则行尾锚点），**Android 的 ICU 引擎判定为语法错误**。
桌面 JDK 容错能通过，所以本地/编译期完全测不出来，**只有真机（Android 16）才崩**。

**为什么发一次链接就再也进不去**：
`firstUrl` 在 `MsgAdapter.getView` → `bind()` 中对**每条**消息调用，
渲染到那条含链接的历史消息时抛异常 → 主界面列表布局阶段崩溃。
那条消息永久留在历史里，所以**每次启动都在同一处崩溃**，表现为"之后就进不去了"。

### 修复（1）根因：不再使用正则
`firstUrl` 改为调用新的 `trimTrailingPunctuation(String)`，
用**纯字符循环判断**剥尾部标点，半角/全角/中文标点均覆盖，
并保留 URL 有意义的尾部 `$` 与 `#`。**从此不再有正则语法风险**。
行为已用 13 组用例 + 全角标点 + null/空/纯标点验证全部通过。

### 修复（2）兜底：单条消息渲染失败不再拖垮整个列表
`MsgAdapter.getView()` 包 try-catch，某一行 `bind()` 失败时记 log 并清空该行控件显示，
**保证 App 始终可进入**，不再因任何单条脏数据导致永久闪退。

versionCode 17 / versionName 1.7.6，签名未变，可直接覆盖安装。
**历史消息中的链接无需清理**，新版本能正常渲染。

## v1.8.0 变更（2026-10-4）

### 需求 1：按设备分会话 + 按设备分文件夹（类微信多会话）

**改造前的真实状况**（不是猜测，是逐项核对代码后的结论）：

| 维度 | Windows 端 | Android 端 |
|---|---|---|
| 聊天记录分文件存储 | ✅ 早已按 peerId 分 `history/<id>.jsonl` | ✅ 早已按 peerId 分 `history/<id>.jsonl` |
| 界面按设备隔离 | ✅ 早已有 `_visible_msgs()` 过滤 | ❌ **所有设备消息混在一个列表**，Spinner 只是发送目标选择器 |
| 接收文件分设备文件夹 | ❌ 全部落在同一个 `save_dir` | ❌ 全部落在 `Download/FlashDrop/` |

所以本次实际要补的缺口是：**① Android 界面没按设备切分 ② 双端接收文件都没分设备文件夹**。

#### Android 界面隔离实现

`msgs` 保持**全量数据源**（索引 `byTidIn/byTidOut/byMid` 完整），新增 `viewMsgs` 作为
「当前选中设备」的**投影**。这样切设备不用重读磁盘，传输状态索引也不会丢。

所有改动 `msgs` 的地方统一走 `refreshChat()`（= `rebuildView()` + `notifyDataSetChanged()`）——
**忘记重建投影会导致"全部设备"能看见、切到单设备却看不到**，这是本改造最容易踩的坑。

设备选择栏（Spinner）升级为**会话切换器**：选中哪台，聊天区只显示那台的内容，发送也只发给它。

**消息归属判定（三条规则，缺一不可）**：

| 规则 | 条件 | 为什么需要 |
|---|---|---|
| 1 | `dir=in` → `peerId` 即发送方 | 收到的消息天然属于对方会话 |
| 2 | `dir=out` → `targets` 含该设备 | 群发时**每个目标都应看到自己那条** |
| 3 | 目标与 peerId 皆空 → 所有会话可见 | 分享入口直发/历史脏数据；**否则用户切设备会以为消息凭空消失** |

> 规则 3 是测试先失败才发现的：`sendText` 把 `peerId` 设为 `targets.get(0)`，
> 无目标消息在任何单设备视图都不可见。已修。

#### 按设备分文件夹（双端）

| 端 | 落盘路径 |
|---|---|

## v1.9.0 变更（2026-10-4）——异步发送保存窗口

### 需求

> 电脑和手机端，在选择全部设备发送时，如果没有在线设备，先发出去在对话框保存，待连接设备以后再传输，作为一个异步发送保存的窗口。

### 改造前现状（先核对，不凭印象动手）

| 能力 | v1.8.0 状态 | 问题 |
|---|---|---|
| 文件待发队列 | ✅ 已有（`pending_files`） | — |
| **文本待发** | ❌ **完全没有** | 零在线时 `_guard_targets()` 弹「没有在线的目标设备」直接拦死，输入的文本**丢失** |
| 「全部设备」待发语义 | ⚠️ 只发第一台 | `main_window.py:1366` 是 `targets = online[:1]`，注释写「未指定目标：发给第一台上线设备」——用户选的是**全部设备**，上线 3 台只发 1 台，另外 2 台永远收不到 |
| 待发送管理窗口 | ❌ 无 | 只能右键单条取消，无法查看队列全貌、无法手动立即发送、无法批量清空 |
| Android 文本待发 | ❌ 无 | `sendText()` 同样 toast 拦死 |

### 实现要点

**1. 队列结构统一（双端同构）**

```json
{ "type": "text"|"file", "text": "…", "paths": [...],
  "targets": [peer_id...], "broadcast": true, "ts": 1700000000, "mid": "…" }
```

`targets` 为空 + `broadcast=true` = **群发语义**（上线即发给当时所有在线设备）。
旧版本条目无 `type`/`broadcast` 字段 → 按 `file` + 群发处理，**向后兼容无需迁移**。

**2. 目标解析规则（双端严格一致）**

| 场景 | 目标 |
|---|---|
| `broadcast=true` 或 `targets` 为空 | **所有在线设备**（群发） |
| 定向且部分在线 | 仅已上线的那几台 |
| 定向且全部离线 | 不发，**保留在队列**等它们上线 |

**3. 关键修正：群发不再只发第一台**

v1.8.0 `_flush_pending()` 的 `online[:1]` 已改为「发给当时所有在线设备」，Android 端 `recentOnlinePeerId()` 单设备逻辑同样移除。RT190 / verify_v190 用 8 组场景对拍双端结论。

**4. 聊天区待发送气泡**

文本与文件统一 `state="pending"`：气泡下方显示「⏳ 待发送 · 全部设备上线后自动发出」/「· 目标设备上线后自动发出」+ **取消**按钮。Windows 挂在 `BubbleFrame._apply_text_state()`，Android 补齐了文本分支的状态文案与操作按钮（`item_text_out.xml` 原先没有按钮行，已加）。

**5. 待发送管理窗口**

| 端 | 入口 | 能力 |
|---|---|---|
| Windows | 顶栏「⏳ 待发送 N」 | 独立对话框，列出每条的类型/摘要/目标名/时间；**立即发送 / 删除此项 / 清空全部**（清空二次确认） |
| Android | 顶栏「待发送 N」（无内容时隐藏） | 点击条目 → 弹出「立即发送 / 删除」；**清空全部**走二次确认 |

**6. 补发后不留空窗**

文本待发补发成功时，Android 端通过 `flushPendingSends(onSent)` 回调补写正式发送消息（`persist` 入历史），Windows 端 `_flush_pending` 直接调 `_out_text_msg`，两端都是「待发送气泡消失 → 正式消息出现」。

### 过程中发现并修复的真实缺陷

| 缺陷 | 发现方式 | 根因 |
|---|---|---|
| **文件入队路径直接崩溃** | `verify_v190_ui.py` 阶段 A 抛 `TypeError` | `_entry_text` 是 `@staticmethod` 却调用 `MainWindow._queue_kind(entry)`，而后者是实例方法 → 缺 self 参数。**纯文本路径测不到**，只有发文件才触发。已把 `_queue_kind` 也改为 staticmethod，并在 `verify_v190.py` 加 AST 静态校验防回归 |
| Android 摘要与 Windows 不一致 | 跨端口径对拍 | Android `uris.size() > 1` 就折算数量，Windows 是 `> 3`。统一为 Windows 口径（≤3 全列出，>3 才折算），并把文件名净化下沉到 `FdUtil.uriDisplayName()` 供两处复用 |
| 群发只发第一台 | RT190 专项断言 | 见上「改造前现状」，v1.8.0 的设计缺陷，v1.9.0 修正 |

### 问题 2 根因：文件删了但记录还在

`MainActivity.doScopedDelete()` 在 v1.10.0 里是**三条互不相干的分支**：

| 分支 | v1.10.0 行为 | 结果 |
|---|---|---|
| `delChat` | 调 `deleteMsgs()`（会从 `msgs` 移除） | ✅ 记录消失 |
| `delFile` | 只调 `FdUtil.deleteByIdentities()` 删**历史文件条目** | ❌ **从不碰内存 `msgs` → 气泡记录原封不动** |
| `delImg` | 同上 | ❌ 同上 |

也就是说：**磁盘文件删了、历史文件删了，但内存里的消息对象从来没被摘掉**，
所以用户看到"文件没了、记录还在"。

**v1.10.1 改为三类统一走「摘除 + 清理」路径**：

| 新增/改动 | 说明 |
|---|---|
| `detachMsgs(Set<String> keys)` | 主线程：从 `msgs` 里 `removeIf` 真正摘除；**同步清理 `byMid` / `byTidIn` / `byTidOut` 三个索引**——否则后续到达的传输进度事件会把已删消息"复活" |
| `purgeMsgs(List<Msg> gone, Set<String> keys)` | 后台线程：`deleteLocalFileOf()` 删对应磁盘文件 + `deleteByIdentities()` 清历史文件条目，返回删除文件数 |
| `tidOf(String key)` | 从 `keyOf()` 生成的 `ts\|midOrTid\|dir\|kind` 里还原 tid，供索引清理使用 |
| `doScopedDelete()` 重写 | 先按「作用域 + 勾选类型」用 `categoryOf()` 挑出全部 key → `detachMsgs()` + `refreshChat()`（**界面立刻干净**）→ 后台 `purgeMsgs()` + `deleteSavedFiles()` 清磁盘残留 → UI 线程 Toast 汇总"X 条记录、Y 个文件" |

> 顺序很关键：**`detachMsgs()` 必须在 `refreshChat()` 之前**（否则界面刷完还是旧的），
> **磁盘 IO 必须在后台线程**（否则删除卡界面，正是 v1.10.0 设置页"点着像没反应"的同款毛病）。

## v1.12.0 变更（2026-10-4）——重复接收修复 + 图片显示修复 + 对齐统一 + 赞助支持

### 问题 1：电脑发送了一次的图片，安卓接收了两次【根因修复】

**排查结论**：Windows 端历史记录实锤只发了 1 次（同一条 tid 落盘仅一个文件、一条 JSONL 记录），
重复只发生在安卓聊天记录里——**FlashNode 层按 `peerId|tid` 去重可靠，是 UI 层竞态**。

**根因链**：`MainActivity` 切换会话时 `byTidIn.clear()`（内存索引）+ `loadHistory()` 异步重建
（后台线程 + `ui.post` 回灌）。在这个窗口期内，同 tid 的 recv 事件到达 → `byTidIn.get(tid)==null`
→ 误判为新消息 → new 第二条 Msg → append 上屏 + persist 固化进历史，下次加载又再重复。

| 层 | 修复 |
|---|---|
| 事件兜底查重 | recv 找不到 `byTidIn` 索引时，先在 `msgs` 里按 `kind=file && dir=in && tid` 全量扫一遍，命中则复用旧 Msg（回填索引），不再新建 |
| 历史加载去重 | `loadHistory` 排序后倒序扫描，`file` 类消息按 tid `HashSet` 去重（保留最早一条），彻底清掉已固化的重复记录 |

### 问题 2：图片打开显示不正确（竖图偏上半屏、下半黑）【根因修复】

**根因**：`ImageViewerActivity.applyMatrix` 只做了 `postScale + postTranslate(transX, transY)`，
**缺居中平移**——图片左上角钉死在 (0,0)，竖长图只显示在屏幕上半部。

修复：`applyMatrix` 改为 `postScale(s) → postTranslate(居中偏移 + transX/Y)`，新增
`centerOffset(bw, bh, s)` 计算居中量；缩放/双击的锚点公式同步带入居中项
（`transX = fx - cn[0] - (fx - co[0] - transX) * k`，co/cn 为缩放前后居中偏移），
保证捏合/双击仍以手指位置为锚；首帧布局未完成时 `root.post` 延迟重算。
另加 **EXIF 方向防御**：`ExifInterface` 读取旋转标记，90/180/270 自动转正（手机相机直拍图不再横躺）。

## v1.13.0 变更（2026-10-5）——图片过小/按钮位置/重复接收/文字对比度/待发送行内化

本版修的是 **v1.12.0 引入的两处真回归**（问题 1、2）与三项体验问题（3、4、5）。
用户升级 v1.12.0 后在真机上复现，逐条定位如下。

### 问题 1：图片打开还是小的，不是完整铺满【根因修复】

**现象**：打开截图，图片只占屏幕中间一小块（实测约占屏 16.7%），不是铺满可视区。

**根因（算术实锤）**：`fitToScreen()` 里有一句"上限保护"——
`if (baseScale > 1f) baseScale = Math.min(baseScale, 1f);`（注释写的是"别把小图放成马赛克"）。
而 `showIndex()` 会先用 `loadThumb()`（`inSampleSize=8` 的聊天列表缩略图）占位：

| 阶段 | 尺寸 | baseScale 计算 | 结果 |
|---|---|---|---|
| 缩略图占位 | 1440×3088 → **180×386** | min(1080/180, 2340/386) = **6.0** | 被 1.0 砍掉 → 按 180×386 显示（占屏 16.7%）|
| 高清图 | 1440×3088 | min(1080/1440, 2340/3088) = 0.75 | 正常铺满（100%）|

占位图这条路径把基准缩放锁死在 1.0，用户看到的就是那张 180×386 的小图。

**修复（两处）**：
1. **去掉 1.0 封顶**：图片查看器的职责是尽量铺满可视区，放大略糊远好于小得看不清；
   用户仍可捏合缩小回 1.0 倍看原始像素。
2. **换掉占位图来源**：不再用 `loadThumb`（1/8 采样），改为新增的 `decodeForScreen()`
   按屏幕长边采样解码过渡图（清晰度够、解码也快），避免"占位必糊 + 高清失败就永远糊"。

### 问题 2：保存/转发按钮不在底部【根因修复 · 一行致命 bug】

**现象**：图片查看器底部空空如也，操作按钮看不见（用户描述为"按钮还在顶部"）。

**根因（代码实锤）**：`ImageViewerActivity.buildBottomBar()` 结尾——

```java
FrameLayout.LayoutParams lp = new FrameLayout.LayoutParams(MATCH_PARENT, WRAP_CONTENT);
lp.gravity = Gravity.BOTTOM;
return outer;   // ← lp 配置好了，却从未应用到 outer 上！
```

`lp` 创建后被直接丢弃（注释还写着"外层自身 gravity 由 lp 决定"，与实际相反）。
对照 `buildTopBar()` 结尾用的是 `return wrap(bar, lp);` —— 顶栏正常应用了 `Gravity.TOP`，
底栏则带着默认 `LayoutParams`（`gravity=TOP|LEFT`）被塞进 FrameLayout，高度也塌成 wrap_content，
**底栏被压在左上角、与图片层重叠而不可见**。

**修复**：改为 `return wrap(outer, lp);`，与顶栏写法对齐。

### 问题 3：图片发送一次，手机仍接收两遍【查重加固】

**根因**：一次文件接收会先后产生 `offer → confirm → started → progress… → done` **多个 recv 事件**，
它们共享同一个 `tid`，本应合并成一条气泡。但安卓端的 `byTidIn` 只是一份**内存索引**，
会在切换会话 / 加载历史时被 `clear()`——窗口期内后续事件找不到索引就直接 `new` 出第二条。

**修复（三层防线）**：
| 层 | 做法 |
|---|---|
| 判定统一 | 新增 `isSameInboundFile()`：以 tid 为准；tid 缺失时退化为「文件名 + 大小」双匹配（避免空 tid 把不同文件误合并） |
| 事件查重 | 内存索引命中后仍要过 `isSameInboundFile` 校验；未命中**无条件回扫** `msgs` 列表 |
| 渲染兜底 | `rebuildView()`（所有上屏的唯一汇流点）按 tid 唯一化，重复副本挡在屏幕之外 |

> 注：Windows 端 `FlashNode` 层本就按 `peerId|tid` 去重、磁盘只落 1 个文件，
> 重复只发生在安卓的聊天记录层。

### 问题 4：气泡内文件信息溢出 + 颜色对比度不足

**现象**：绿色气泡里的 `HaoStation · 142.9 KB` 等小字压出气泡边界，且灰字在亮底上发虚看不清。

**根因（两条）**：
1. **宽度约束打架**：子 View 各自设 `android:maxWidth="280dp"`、进度条固定 `260dp`，
   而代码又把 `msg_meta` 的 maxWidth 设为「屏宽 × 0.62」（1080 屏 ≈ 670px）。
   多个子 View 各自争宽，把 `wrap_content` 的气泡撑破 → 文字溢出。
2. **前景色写死主题灰**：`h.meta.setTextColor(t.dim)`，而 `t.dim`（`#9CA3AF`）是给**深色页面背景**
   设计的；气泡一旦换成自定义方案色（微信绿等浅色），灰字对比度骤降。

**修复**：
- **宽度**：4 个布局（`item_text/file_in/out`）统一改为**约束气泡容器自身** `maxWidth`，
  子 View 全部去掉硬编码宽度，进度条改 `match_parent` 跟随气泡。
  （约束容器才是正确做法——子 View 各自设 maxWidth 必然互相竞争。）
- **颜色**：`FdTheme` 新增三个按底色推导前景色的工具，用感知亮度（BT.601）判断底色明暗：
  - `onColorText(bg)` → 主文字（深底白字 / 浅底深字）
  - `onColorDim(bg)` → 次级文字（大小、状态）
  - `onColorAccent(accent, bg)` → **语义色适配**：成功绿/失败红/等待黄保持色相不变，
    仅按底色压暗或提亮，保证与底色亮度差 ≥ 0.35

## v1.13.1 变更（2026-10-5）——后台收到文件聊天框空白 / 消息卡在"发送中"

用户实测报障（原文）：
> 安卓版后台在线时 接收到文件信息 有提示 可以点进来 但是对话框没有东西 但是文件都已经存在手机文件夹内了 需要检查修复

### 根因分析

| # | 现象 | 根因 | 位置 |
|---|---|---|---|
| A | 后台收到文件 → 点通知进来对话框空白 | `NodeService.handleBackgroundEvent()` **只弹系统通知，不写历史、不写内存列表**。"记录入库"这条腿整个是断的：文件本体由 `FlashNode` 底层正常落盘（所以能在手机文件夹里看到），但 `history/*.jsonl` 里没有任何记录。点通知回到界面后 `loadHistory()` 从磁盘读不到东西 → 空白 | `NodeService.java` |
| A2 | 数据层补刀 | `persist()` 里 `if (m.peerId == null \|\| m.peerId.isEmpty()) return;` —— 接收路径的 `peer_id` 来自事件字段，协议缺字段时是空串，记录被**静默丢弃** | `MainActivity.persist()` |
| B | 消息发出去了，状态一直"发送中…" | `ack` / `text_state` 只查内存 `byMid`，而该索引在切会话、`loadHistory` 时会被 `clear()`；一旦 miss 就永远改不动状态。且改完**不落盘**，重启后 `loadHistory` 读回的还是 `sending` | `MainActivity` 事件分支 |

| # | 修复 | 说明 |
|---|---|---|
| 1 | 新增 `FlashApp.persistInboundEvent()` | 后台事件统一落库通道：把 `text` / `transfer+recv` 事件转成消息记录写进 `history/*.jsonl`。以 `peerId+mid` / `peerId+tid` 为键**幂等去重**（同一传输的 offer/started/progress/done 只落一条），键集合超 2000 自动清理 |

| 6 | 新增 `FdUtil.upsertHistory()` | 按 `mid`（文本）或 `tid+dir+kind`（文件）就地定位并覆盖历史记录，命中失败才退化为追加 |

| 8 | `handleTransfer` 接收侧 | 新建接收消息时 `peer_id` 空值回落 `__local__`；已上屏条目在状态推进时 `persistState()` |

### v1.18.1 修复（2026-10-6）—— EXE 启动即崩

**用户反馈**：新版 EXE 双击后弹「Unhandled exception in script」。

```
AttributeError: 'Config' object has no attribute 'get'
  File "app\ui\main_window.py", line 524, in __init__
```

**根因**：v1.18.0 为新增截图配置项，在 `MainWindow.__init__` 里写成了
`cfg.get("snip_hide_self", True)`。
运行时 `cfg` 是 **`Config` 对象**，它只实现 `__getitem__` / `__setitem__`，
**没有 dict 的 `.get()`** → 构造主窗口时立刻抛异常。

**为什么没被单测抓到（重点教训）**

| 环节 | 当时做的 | 为什么漏 |
|---|---|---|
| 离屏静态断言 | 用 `inspect.getsource()` 检查源码字符串 | 只验证"文本包含 X"，不是**执行** |
| 配置往返测试 | `Config()` 读写 `snip_hide_self` | 只测了 `Config` 本身，没测 `MainWindow` 用它 |
| **从未做的** | **构造一次 `MainWindow`** / **启动打包产物** | ← 崩溃点就在这里 |

**修复**

| 文件 | 改动 |
|---|---|
| `windows/app/ui/main_window.py` | `cfg.get("snip_hide_self", True)` → `try: cfg["snip_hide_self"] except (KeyError, TypeError): True`（兼容老配置文件缺键） |

**已确认全仓无同类隐患**：`grep` 全部 `self.cfg` 用法，其余均为 `self.cfg[...]` 或
`self.cfg.save_dir` / `ensure_dirs()` 等真属性/方法，无第二处 `.get()` 误用。

**新增两道防线（从此类事故不可再犯）**

| 新增 | 内容 |
|---|---|
| `verify_v1180_snip.py` §7b | **真实构造 `MainWindow`**（正线上崩溃点）：默认值 / 老配置缺键回落 / 显式 False 读回，共 **8 条**断言。原先 62 项 → 现 **70 项** |
| **`windows/tests/smoke_exe.py`（新建）** | **直接启动打包后的 `FlashDrop.exe`**：进程存活 ≥14s、无 `AttributeError`/`Traceback`/`Unhandled exception` 输出、`config.json` 正确落盘（含新键）、端口 58899 LISTENING、可正常终止 —— **13/13 通过** |

### 二、定位报错来源

报错文案出自 `MainActivity.java` 中 `doInstallApk()` 末尾的兜底分支：

```java
toast("未找到可用的安装程序，请先在系统设置中允许安装未知应用");
```

该逻辑 **v1.16.0 就存在，v1.18.0 一字未改**。所以不是"新版改坏了"，
而是**环境漂移**放大了代码里两个先天缺陷。

调用链：

```
点文件卡片 → openFile(m)
  → installApk(m)       先查 canRequestPackageInstalls()，未授权则弹窗引导
  → doInstallApk(uri)   三级探测都失败 → 落到兜底 toast
```

### 三、根因（两个先天缺陷）

**缺陷 ①：探测意图与启动意图语义不一致**

```java
Intent probe = new Intent(base);
if (probe.resolveActivity(getPackageManager()) == null) return false;
```

`base` 若不带 MIME，copy 后 `type` 仍为 null，探测语义退化成"有没有应用能打开
这个 `content://`"，与实际 filter 匹配不一致。且 `resolveActivity` 在部分国产
ROM 上对「content:// + 第三方 authority」会给出**假阴性** —— 明明 chooser 能
列出应用却返回 null。

**缺陷 ②：`ACTION_INSTALL_PACKAGE` 在国产 ROM 上已被移除**

`ACTION_INSTALL_PACKAGE` 是 Android 7 之前的老入口。Android 9+ 起
MIUI / ColorOS / EMUI / OriginOS 多数已移除对该 action 的声明，系统安装器改为
只注册 `ACTION_VIEW` + `application/vnd.android.package-archive`。
**于是第 ③ 级必然 `false`。**

叠加第 ① 级在国产 ROM 上也常 `false`（安装器对**第三方 authority** 的精确
MIME 过滤匹配失败）→ **三级全 false → 兜底 toast**。

### 四、修复：四级放宽 + 计数探测

| 级别 | 意图 | 说明 |
|---|---|---|
| ① | `ACTION_VIEW` + **精确 apk MIME** | 最贴合系统安装器声明的 filter |
| ② | `ACTION_VIEW` + **通配 MIME** | 国产 ROM 的救命稻草 —— 让所有能"打开文件"的应用进候选，安装器必然在内 |
| ③ | `ACTION_VIEW` **不带 MIME** | 交给系统按 `ContentProvider.getType()` 推断 |
| ④ | `ACTION_INSTALL_PACKAGE` | 老系统兜底，故放最后 |

探测方式改造：

- `resolveActivity` → **`queryIntentActivities` 计数**（消除假阴性）
- 候选只有 1 个时**直接启动**，不套 chooser（省一次无意义点击）
- 多候选才 `createChooser(base, "选择安装程序")`

兜底体验改造：

- 旧文案换成 `FdDialog`，给出 **3 条可执行检查项**
  （权限 / 安全中心拦截 / 长按卡片走「其他应用打开」）
- 带「去设置」按钮，直接跳 `ACTION_MANAGE_UNKNOWN_APP_SOURCES`

> 复用 `FdFileOp.openWithChooser` 已验证有效的「逐级放宽」模式，
> 遵循 v1.15.0 确立的"薄委托层、避免两处分叉"原则。

### 五、踩坑：Javadoc 里的 `{@code */*}` 会提前终止注释

写注释时用了 `{@code */*}`，其中 `*/` **提前闭合了块注释**，
导致后面的 `private void ...` 全部被当作代码解析 → **64 个编译错误**。

```

错误: 需要 class、interface、enum 或 record   ×64
```

**修复**：改为纯文字「通配 MIME」。已加入回归断言 §7 防复发。

## v1.18.4 优化（2026-10-7）—— 文本长按改为微信式「选择光标 + 动态菜单」

### 用户需求

> 做成和微信一样的 长按文本内出现可以选择的光标

### 一、交互设计（对齐微信）

```
长按正文 → 系统进入文本选择模式（出现可选择的光标 / 左右把手）
         → 悬浮菜单 = 复制 · 删除 · 多选          ← 消息级

         → 悬浮菜单 = 复制 · 全选                ← 选区级

刚长按那一刻还没动，给消息级的「删除 / 多选」最顺手；一旦拖动把手，

3. **移除中间态**：v1.18.3 的 `m.textSelectable` 开关、菜单项「选择文字」、

  符号: 方法 setSelection(int,int)
  位置: 类型为TextView的变量 tv
```

用 `javap` 核查 `android.jar` 后发现——**这个 jar 里 `TextView` 只暴露了
`getSelectionStart/End()`，没有 `setSelection(int,int)`**：

```
public int getSelectionStart();     ✅
public int getSelectionEnd();       ✅
public void setSelection(int,int);  ❌ 不存在
```

**改用官方途径** —— 选区的本质就是 `Spannable` 上的
`SELECTION_START` / `SELECTION_END` 两个 span：

```java
CharSequence text = tv.getText();
if (text instanceof android.text.Spannable) {
    android.text.Selection.setSelection((android.text.Spannable) text, 0, text.length());
}
```

> `setTextIsSelectable(true)` 会把正文转成 `SPANNABLE`，故 instanceof 判断可稳定通过。

## v1.18.5 修复（2026-10-7）—— 「不能局部复制」根因修复 + 菜单样式对齐微信

### 用户反馈

### 一、根因（两层，缺一不可）

v1.18.4 已经让文本正文 `setTextIsSelectable(true)`（因而 focusable），
但**真正的拦路虎在 ListView 这一层**：

**① `AbsListView` 的 `mItemsCanFocus` 默认为 `false`**

它的含义是"列表假定 item 内**没有**可聚焦控件"，于是**所有触摸事件都由
列表自己消化，绝不向下传递**。文本正文虽然已设为可选，长按却永远到不了
它手上 —— 选择光标不出现，也就无从框选局部文字。

**② `setOnItemLongClickListener` 返回 `true`**

把长按彻底消费掉，连"漏给子控件"的机会都没有。

**两层叠加的后果**：长按被列表吃掉 → 正文收不到 → 无选择光标 → 不能局部复制。

### 二、修复：`chatList.setItemsCanFocus(true)`

开启后，ListView 检测到 item 内有 focusable 子控件时会把事件交给它；
而文本行的 row 因此 `hasFocusable() == true`，
`AbsListView` 的 `CheckForLongPress` 会跳过行级长按 —— **两层正好配套**。

**对文件消息无影响**：文件卡片是自绘 LinearLayout（clickable 但**不可聚焦**），
row 内没有可聚焦控件，事件仍由 ListView 处理，点击/长按照旧走
`setOnItemClickListener` / `setOnItemLongClickListener`。

## v1.18.6 修复（2026-10-7）—— 文本长按选择（第三层：移除气泡拦截）

## v1.18.7 修复（2026-10-7）—— 文件已收到却显示「接收失败」

### 用户反馈

> 电脑给手机端发送文件 电脑端显示已送达 手机端显示失败
> 我是不确定是不是后台是打开的
> 确定了 后台状态下接收不成功
> **文件在 但是显示接受失败** ← 关键：文件其实收到了

### 一、根因：后台落库去重缺陷

`FlashApp.persistInboundEvent()` 负责「前台界面不在时把接收记录落库」，
它按 `peerId|tid` 去重：

```java
String key = peerId + "|" + "t" + tid;
if (bgSeenKeys.contains(key)) return;     // 只落第一条
```

**但一次文件接收会产生一串事件**：

```
offer → confirm → started → progress… → done
```

**第一条 `offer` 被写进历史并占住了 key**，真正代表结果的 `done`
反而被去重**跳过**。

**后果**：用户回到前台读到的是 `state = offer` 的记录 →
文件卡片判定为「未接收」渲染成**虚线态**、文案停在「等待接收…」
→ 看起来就是「接收失败」。

这恰好解释了那几个看似矛盾的现象：
- ✅ 电脑端显示「已送达」（因为 `done` 确实发生过、`verified` 也通过）
- ✅ 手机 `Download/FlashDrop` 里能找到文件（确实落盘了）
- ❌ 唯独**界面状态不对**

> 结论：**接收本身一直是成功的**，错的只是后台那条历史记录的状态字段。

### 二、修复（三处）

| # | 改动 | 作用 |
|---|---|---|
| 1 | **后台落库只认终态**（done/failed/refused/cancelled） | 根因修复，中间态不再占用 key |
| 2 | **UI 状态自愈**：接收侧若 `hasLocalContent(m)` 为真但 state 非成功态，就地修正为 `done` | **让已经写坏的旧记录无需重传即可正常显示** |
| 3 | **got 判定改以本地实况为准**：`hasLocalContent(m) \|\| done` | 「文件在本地」是不会骗人的事实 |

第 2 条尤其重要 —— 用户手机上**已经存在**被写坏的历史记录，
只修根因的话旧记录依然是坏的；自愈逻辑让它自动恢复，**不用删库、不用重传**。
