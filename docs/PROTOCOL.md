# FlashDrop（闪传）局域网传输协议 v1

本协议为 Windows 端（Python）与 Android 端（Java）共同遵守的通信规范。设计目标：

- 纯局域网（LAN）直连，不依赖任何互联网服务器；
- 支持同网段快速发现（UDP 广播 + 组播）；
- 支持**多路由器级联环境**（设备分属不同子网，如路由器 A 下挂路由器 B）：主动扫描 + 双向连接尝试 + 连接复用；
- 多客户端并发收发（多台电脑/手机互传、同步群发）；
- 文本、图片、任意文件传输，分块、校验、可取消。

---

## 1. 基本参数

| 项 | 值 |
|---|---|
| TCP 服务端口 | `58899`（可在设置中修改，两端需一致才能自动发现；手动连接时可指定端口） |
| UDP 发现端口 | `58899`（与 TCP 端口相同，跟随设置） |
| 组播组 | `239.255.0.5`（端口同上） |
| 应用标识 | JSON 字段 `"app":"FlashDrop"`，协议版本 `"v":1` |
| 设备 ID | 首次启动生成的 16 位随机十六进制串，持久保存 |
| 单帧二进制块上限 | 512 KB（524288 字节） |

所有多字节整数均为**大端序**（Big-Endian）。JSON 一律 UTF-8 编码。

---

## 2. 设备发现（UDP）

### 2.1 广播与组播

每个设备每隔 `3 秒` 向以下目标发送 `DISC` 数据报（目标端口一律为本机 UDP 端口）：

1. `255.255.255.255`（受限广播）；
2. 本机每个 IPv4 网卡的**定向广播地址**（如 `192.168.1.255`）；
3. 组播组 `239.255.0.5`（需加入组，Android 端需持有 `MulticastLock`）；
4. `127.0.0.1`（便于同机多实例协作与自测）。

`DISC` 包体为 JSON：

```json
{"app":"FlashDrop","v":1,"type":"DISC","id":"a1b2...","name":"我的电脑","platform":"windows","tcp":58899}
```

`platform` 取值：`windows` / `android`。

### 2.2 收到 DISC 后的行为

1. 记录/更新该设备信息与 `last_seen` 时间戳；
2. 若此前不认识该设备（或尚无活跃 TCP 连接），**单播**回复一份自己的 `DISC`（每设备每 10 秒最多回复一次，防止风暴）；
3. 若与该设备尚无 TCP 连接，发起 TCP 连接（见第 4 节）。

### 2.3 在线判定

- 满足以下任一条件视为在线：UDP `last_seen` 距今 ≤ 15 秒；或存在活跃 TCP 连接（心跳正常）。
- 其余视为离线；TCP 断开后自动重试连接。

## 3. 子网扫描（多路由器级联环境）

级联路由器场景：设备 A 在路由器 1 的 LAN（如 `192.168.1.0/24`），设备 B 在路由器 2 的 LAN（`192.168.2.0/24`），路由器 2 的 WAN 口接路由器 1 的 LAN 口。此时：

- 广播/组播不能跨路由器（B 的广播到不了 A）；
- B → A 方向的 TCP 通常**可达**（路由器 2 对内做了 NAT，出站无阻）；A → B 方向默认不可达；
- 结论：**只要单向能连上，双向传输即可复用同一条 TCP 连接完成**（全双工）。

### 3.1 扫描策略

1. 触发时机：启动后立即一次；此后每 30 秒后台一次（低并发）；用户点击"刷新设备"立即一次。
2. 目标网段：
   - 本机每个网卡的直连子网（如 `192.168.1.0/24`）；
   - 默认网关所在子网；
   - 常见家用/办公子网清单：`192.168.0.0/24` ~ `192.168.31.0/24`、`10.0.0.0/24`、`10.0.1.0/24`、`10.0.2.0/24`、`172.16.0.0/24` ~ `172.31.0.0/24` 中的主子网；
   - 历史上发现过设备并成功连接过的子网（记入 `known_subnets`，优先扫描）。
3. 方式：对每个候选 IP 的 TCP 端口并发 `connect`（并发 ≤ 128，单连接超时 400ms）。连接成功后立即按第 4 节完成 `HELLO` 握手，确认是 FlashDrop 设备（收到合法 `HELLO` 才保留连接，否则立即关闭）。
4. 扫描仅做"发现新设备"，不对已有连接的 IP 重复连接。

### 3.2 手动连接（兜底）

用户可在"添加设备"中输入 `IP[:端口]` 直接发起 TCP 连接，用于极端网络环境（如 AP 隔离、非常规网段）。

## 4. TCP 连接管理（穿透核心）

### 4.1 握手

TCP 连接建立后，**双方立即**（1 秒内）互发一条 `HELLO` JSON 帧：

```json
{"app":"FlashDrop","v":1,"type":"HELLO","id":"...","name":"...","platform":"windows","tcp":58899}
```

- 任一方在 5 秒内未收到合法 `HELLO`，或 `app` 字段不是 `FlashDrop`，立即断开；
- 握手完成后连接进入活跃状态，开始心跳。

### 4.2 双向尝试与连接去重（关键规则）

互为邻居的两台设备都会尝试主动连接对方（因为任何一方都可能处于"可达"位置）。为避免重复连接，规定：

> **设备 ID 较大的一方作为"首选发起方"。** 对本机而言，与设备 P 的连接中，"首选连接"是：
> - 若 `my_id > P.id`：由本机主动发起的（outgoing）连接；
> - 若 `P.id > my_id`：由对方主动发起（本机 accept 的，incoming）连接。

新连接建立（或握手完成）时与现有连接比较：

- 新连接是首选而旧连接不是 → 关闭旧连接，采用新连接；
- 新连接不是首选：若已有任何活跃连接 → 关闭新连接；若没有 → 采用新连接（兜底，覆盖单向可达场景）；
- 双方按同一规则对称执行，最终收敛为"至多一条活跃连接"，且在单向可达时仍能保住那条唯一可用的连接。

### 4.3 心跳

- 每 10 秒发送 `{"type":"PING"}`，对方回 `{"type":"PONG"}`；
- 连续 30 秒未收到对方任何帧（PING/PONG/数据均可刷新）→ 判定死链，关闭并转入重连队列（指数退避：1s、2s、4s…上限 30s）。

## 5. TCP 帧格式

TCP 流为由**帧**顺序组成。每帧格式：

```
[4 字节大端 长度 L][L 字节 payload]
```

`payload` 的第 1 字节为**类型字节**：

| 值 | 含义 | payload 其余部分 |
|---|---|---|
| `0x4A` (`'J'`) | JSON 消息 | UTF-8 JSON 文本 |
| `0x42` (`'B'`) | 二进制文件块（顺序流） | 见 5.1 |
| `0x43` (`'C'`) | 带块号的二进制块（断点续传） | 见 5.2 |

### 5.1 顺序流块（`0x42`，v1 原有）

```
[2 字节 tid 长度 n][n 字节 tid UTF-8][8 字节大端 数据长度 m][m 字节数据]
```

语义是**顺序追加**：接收端只能往`.part` 末尾写。断线后已收数据无法复用，
重传只能从 0 开始。保留此类型用于与不支持断点续传的旧版本互操作。

### 5.2 带块号块（`0x43`，v1.18.18 新增，断点续传核心）

```
[2 字节 tid 长度 n][n 字节 tid UTF-8][4 字节大端 块号 index][8 字节大端 数据长度 m][m 字节数据]
```

与 `0x42` 的唯一区别是 tid 之后多一个 4 字节块号。接收端据此
`seek(index × 512KB)` 写入，**块间不再有顺序依赖**：

- 重连后发送方只补发缺失块，已收块直接跳过；
- 重复收到同一块必须**幂等丢弃**（不得重复写入，不得报错）；
- 位图（哪些块已落盘）由接收端持久化，见 6.5。

块长规则：`index < N-1` 的块固定 512KB；末块为 `size - (N-1)×512KB`（可短）。
块数 `N = ceil(size / 512KB)`，`size = 0` 时约定 `N = 1`。
**块长必须与该规则一致**，接收方发现不符即降级为顺序流模式。

> L 的上限为 `1 + 2 + 64 + 4 + 8 + 524288`（约 512 KB + 最大帧头），超长帧视为协议错误，断开连接。

**写入原子性**：一帧的长度头与内容必须一次性写入（发送方用每连接一把写锁保证多任务并发时不交错）。

## 6. 消息类型（JSON）

### 6.1 会话类

| type | 字段 | 说明 |
|---|---|---|
| `HELLO` | id, name, platform, tcp | 握手 |
| `PING` / `PONG` | — | 心跳 |
| `BYE` | — | 主动退出，对方收到后不再自动重连，直到再次发现 |

### 6.2 文本消息

```json
{"type":"TEXT","mid":"<uuid>","text":"内容","ts":1760000000000}
```

接收方回执：`{"type":"ACK","mid":"<uuid>"}`。

### 6.3 文件传输

一次文件传输由唯一 `tid`（uuid）标识，过程：

```
发送方                              接收方
  |-- FILE_START {tid,name,size,mime,idx,attempt} -->|
  |                                           |-- （自动接收 或 等待用户确认）
  |<-- RECV_READY {tid,idx,have,total,recv} / REFUSE --|
  |-- 带块号块(0x43: tid,index,chunk) x N ------->|
  |-- FILE_END {tid, md5} ------------------->|
  |<-- FILE_OK {tid,path} / FILE_FAIL {tid,reason} --|
```

| 消息 | 字段 | 说明 |
|---|---|---|
| `FILE_START` | tid, name, size, mime, **idx**, **attempt** | name 为 UTF-8 原始文件名（含扩展名，接收方需过滤非法字符），size 字节数，mime 为 MIME 类型（未知填 `application/octet-stream`）。**`idx=1` 表示本端支持 `0x43` 带块号分块**；**`attempt` 为本次是第几次尝试（从 0 开始），仅用于对端日志/UI** |
| `RECV_READY` | tid, **idx**, **have**, **total**, **recv** | 接收方已准备好写盘（自动接收时立即回；手动确认时用户点"接收"后回）。**发送方必须等到此消息才开始发块**。`idx=1` 时 `have` 携带已收块位图（见 6.5）、`total` 为总块数、`recv` 为已落盘字节数 |
| 带块号块 | tid + index + 数据 | `0x43` 帧，每块 ≤ 512 KB，块号从 0 连续递增 |
| `FILE_END` | tid, md5 | 发送完毕；md5 为**全量文件** MD5 小写十六进制（**续传时也必须是全量摘要**，跳过未重发的块也要计入；为空则跳过校验） |
| `FILE_OK` | tid, path, **verified** | 接收方已落盘并通过校验，path 为接收端保存路径。`verified=false` 表示回读校验未通过，发送方须按失败处理 |
| `FILE_FAIL` | tid, reason | 校验失败/磁盘错误等，接收方删除 `.part` 及全部续传状态 |
| `REFUSE` | tid, reason | 接收方拒绝（未开启自动接收且用户点了拒绝/确认超时）。在 RECV_READY 阶段或传输中途均可能收到。**收到即不可重试** |
| `CANCEL` | tid | 任一方取消；发送方停止发送，接收方删除 `.part` 及续传状态 |

**接收落盘规则**：先写缓存目录 `tid.part` → 校验（size，如有 md5 则比对）→ 移动/重命名到保存目录；保存目录中重名时自动追加 ` (1)`、` (2)`…

**并发**：同一连接上多个 tid 的块可交错；每连接同时活跃的接收任务不限，发送端每设备每任务独立限速（默认不限速）。

### 6.5 断点续传与自动重试（v1.18.18 新增）

#### 能力协商

发送方在 `FILE_START` 里带 `idx=1` 声明支持 `0x43`。接收方据此选择模式并回`RECV_READY`：

- 回 `idx=1` → 双方都用 `0x43`，走断点续传路径；
- **不回 `idx`**（旧版本接收方）→ 双方自动退回 `0x42` 顺序流，传输照常完成。

协商结果**仅对本次传输有效**，不得跨传输缓存（多传输并发时会互相污染）。

#### 接收端续传状态

| 文件 | 位置 | 作用 |
|---|---|---|
| `tid.part` | 缓存目录 | 首次接收即 `truncate(size)` **预分配到完整大小**，收到的块按 `index×512KB` seek 写入 |
| `tid.bmp` | 缓存目录 | 块位图，第 i 位=第 i 块已落盘。原子写（`.bmp.tmp` + replace） |
| `tid.fp` | 缓存目录 | 续传指纹 = `md5(size + "|" + 文件名)[:16]`，防止同名不同内容的文件被错误拼接 |

`.part`、`.bmp`、`.fp` **三者一致**时才恢复续传（校验指纹、`.part` 实际大小 == 声明 size、位图可读）；任一不符即**全部清理重来**。

位图落盘节流：每收满 16 块或距上次落盘超过 2 秒落一次；断线、结束、续传等关键节点强制落盘。

**已收字节数必须由位图与块号推导，不得累加**（否则重复块会导致计数漂移）。

#### 断线与清理时机

| 情形 | `.part` / `.bmp` / `.fp` |
|---|---|
| 连接中断 | **保留**（可续传） |
| `FILE_END` 后 MD5 校验失败 | 全部删除 |
| 收到 `CANCEL` / `REFUSE` | 全部删除 |
| 手动确认超时未接收 | 全部删除 |
| 传输成功 | 全部删除 |
| 超过 7 天且无在途任务 | 全部删除（周期 GC） |

#### MD5 校验的两种模式

- **顺序流模式**（老端/块长不符降级）：增量 `hashlib.md5()` 边收边算，与 `FILE_END` 的 md5 比对；
- **带块号模式**：所有块到齐后整体读文件计算 MD5 比对（因为块可乱序到达，增量摘要无意义）。

#### 发送端自动重试

外层重试循环包裹单次发送：

- **可重试**：设备不在线、连接中断、等待超时。指数退避 `1.5^n`秒（上限 30s），**最多 3 次**；
- **不可重试**：对方 `REFUSE` / `CANCEL`、源文件不可读。立即失败，不重试。

重试**沿用同一个 `tid`** —— 接收端凭 `tid` 找回 `.part` 与位图，只补缺失块。
每次重试在 `FILE_START.attempt` 中体现次数，接收端可用于 UI 提示。

> ★ 实现要点（两端都必须遵守，否则功能静默失效）：
> 1. 跳过集合 = **已收到的块** = `全部块 - missing()`。把`missing()`（待发块）当跳过集会**一个块都不发**。
> 2. `md5.update()` 必须在"发送/跳过"判断**之外**，对所有块执行，保证 `FILE_END` 是全量摘要。
> 3. 续传进度基准 = 已收字节数，否则进度条会倒退。

### 6.4 错误与兼容

- 未知 `type` 的 JSON 消息：忽略（向前兼容）；
- 无法解析的帧：断开该连接；
- `v` 大于本端支持版本的 `HELLO`：仍接受连接，忽略不认识的字段。

### 6.6 设备备注 / 别名（v1.18.18 新增）

```json
{"type":"ALIAS","name":"我的手机"}
```

- **本机备注只存在本地**（配置项 `peer_aliases: {peer_id: 名称}`），用于本地显示；
- `name` 为空串表示清除备注；
- ★ **本端从不因为收到 `ALIAS` 而改写自己的设备名**，也**不自动把自己看到的备注回传**。
  理由：两端各自给对方的备注独立维护，若互相回传会形成乒乓覆盖，用户在A 端改名会把B 端的备注也冲掉。
- 显示优先级：`本机备注 > 对端自报名 > peer_id 前8 位`。

> 消息类型与协议常量已预留（`T_ALIAS`），但 v1.18.18 **不实现自动同步**，
> 保持备注 purely本地。此条仅作行为约定，避免后续实现踩坑。

## 7. 多端同步发送

发送端 UI 可多选目标设备（或选择"全部设备"）。对每个目标：

- 使用**同一个 tid**、各自独立的 TCP 连接与发送协程并行传输；
- 任一目标失败不影响其他目标；
- UI 聚合展示各目标进度与完成状态。

## 8. 安全说明

- 本协议仅在局域网内通信，不含鉴权；任何局域网内运行本协议的设备均可被发现与互传（与微信文件助手的使用模型一致）；
- 如需基础防护，可在设置中开启"仅允许已配对设备"（v1.1 预留，字段 `HELLO.pair`）。

## 9. 目录与配置

### Windows

- 配置：`%APPDATA%\FlashDrop\config.json`
- 接收保存目录（默认 `%USERPROFILE%\FlashDrop\收到的文件`，可改）
- 传输缓存目录（默认 `%USERPROFILE%\FlashDrop\cache`，可改）
- 聊天记录：`%APPDATA%\FlashDrop\history\<peer_id>.jsonl`

### Android

- 配置：`SharedPreferences`（`flashdrop_prefs`）
- 接收保存目录：`Download/FlashDrop`（API ≥ 29 经 `MediaStore` 写入；API < 29 直接写公共 Download）
- 传输缓存：`context.getCacheDir()/flashdrop/`
