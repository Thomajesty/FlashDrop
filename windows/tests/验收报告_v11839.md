# FlashDrop v1.18.39 验收报告 —— 接收/发送「一次变两次」根治

**日期**：2026-11-23
**触发**：用户反馈（v1.18.38 截图）：手机发一张图，Windows 端收到两张一模一样的卡片（1000407393.jpg · 983.8 KB × 2）。要求同时核对发送方向是否同样重复。

---

## 一、根因（两端同病，代码实锤）

待发队列（离线补发）每轮重试都**重新生成全新 tid**：

- 安卓：`FlashApp.flushPendingSendsAsync` → `FlashNode.sendFileSync` 每次调用 `FdUtil.shortUid()` 生成新 tid
- Windows：`MainWindow._flush_pending` → `node.send_files_sync` 每轮 `util.gen_uid()` 新 tid

接收端其实早把文件收下了，但 FILE_OK 回程丢失（或发送端等 OK 超时）时，队列条目按「确认送达才移除」设计保留重试——下一轮**新 tid** 让接收端的「同 tid 幂等应答」完全失效 → 接收端**真收第二次**：多一张卡片 + 多一份文件。用户数据里见过 `attempt=57` 的队列条目，理论上就是 57 次重复风险。

雪上加霜的两处接收端缺陷：

1. **Windows 幂等表是 pop 一次性**（v1.18.19 `_recent_done.pop(tid)`）：同 tid 第 3 次重试就失效，且键无 peer_id 有撞车理论风险、无容量淘汰。
2. **Windows 接收端无「同 tid 卡片复用」**：本机重启后 `in_by_tid` 清空，同 tid 重发会 new 出第二张卡（安卓端 v1.13.0 早有 msgs 回扫防御，Windows 一直缺失）。
3. **安卓端完全没有幂等表**：Windows 补发同 tid 重试到达时，安卓会整份重收。
4. **两端发送侧都不接受「幂等直答」**：接收端跳过 RECV_READY 直接回 FILE_OK 时，发送端还在傻等 RECV_READY 直到超时（本次 B1 测试当场抓出）。

## 二、修复（v1.18.39）

| # | 端 | 修复 |
| --- | --- | --- |
| 1 | 双端 | **补发稳定 tid 种子**：Windows `send_files_sync(tid_seed=entry["mid"])`，tid=`seed-i`；安卓 `PendingSend.tidSeed`（随队列持久化，懒生成），tid=`seed-序号`。同一队列条目每轮补发 tid 固定 |
| 2 | Windows | `_on_transfer` recv 分支：内存索引未命中时**回扫 msgs 尾部 50 条**复用同 tid 旧卡（标记 `_appended` 防双气泡），对齐安卓 v1.13.0 |
| 3 | Windows | `_recent_done` 改**保留式** FIFO：键 `(peer_id, tid)`，容量 128，不再 pop |
| 4 | 安卓 | 新增 `recvDone` 幂等表（peerId\|tid → 保存路径，容量 128）；`onFileStart` 命中直接回 FILE_OK，不再整份重收 |
| 5 | 双端 | 发送侧等待 RECV_READY 时**与 FILE_OK 竞速**（Windows asyncio.wait 双 future；安卓 `raceReadyOk` 轮询双槽），幂等直答立即当成功收尾 |
| 6 | 安卓 | 手动「立即补发」`pendingSendNow` 也走稳定 tidSeed |

旧数据兼容：存量脏 jsonl 由 v1.18.36 的 load 去重清理，无需迁移。

## 三、验收（verify_v11839_dup_recv.py，36/36 全绿）

**A 组 静态断言 19 项**：两端 tid_seed 链路、持久化、msgs 回扫、`_appended` 标记、幂等表保留式+FIFO、recvDone、竞速。

**B 组 双节点网络行为 10 项**（内存管道双节点）：
- 同 tid_seed 补发 3 次：接收目录始终 1 个文件、started 恰 1 次、三次均 ok（旧 pop 实现第 3 次必失效——已复现并修复）
- tid 恒为 `seed-0`；无种子一次性发送 tid 互不相同（旧行为不变）

**C 组 UI 层 7 项**（offscreen 真窗口）：
- 重启后（in_by_tid 清空）同 tid 重发：仍 1 张卡、状态推进 started→done、新 tid 正常建卡

## 六、已知边界（如实说明）

- 接收端**重启后**同 tid 补发：幂等表（内存）已清空 → 会重收一份文件落盘，但 UI 因修复 #2 只显示一张卡（旧卡被更新为最新路径）。跨重启的完全幂等需要持久化幂等表，当前取舍为不增加磁盘 IO。
- 用户手动「重新发送」（右键旧卡片）仍是新 tid——语义上是用户主动重发，正确。
